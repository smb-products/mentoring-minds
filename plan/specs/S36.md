# S36: open sign-up (Zero's part: server, schema, limits)

Javaris, 2026-11-27 (via OSA): no invite code is needed to join. A new parent account is active right away, adds its
children itself, and can book and do homework at once. An invite code stays optional: it links the parent to the
family Vienne already made, as today. Booking stays a request that Vienne confirms or declines, and she can still
pause a family.

The UI is Axis's tickets (the sign-up "Add your child" step, the gates coming off the parent screens, the landing
copy). This file is the server side they call.

## What changes

### 1. New accounts are ACTIVE

- `prisma/schema.prisma`: `User.status` defaults to `ACTIVE`. `PREVIEW` stays in `UserStatus` for rows made
  before this change. One add-only migration: `npx prisma migrate dev --name open_signup` (it sets the default and
  adds `SignupAttempt`, below). No existing row changes.
- `src/app/(auth)/sign-in/actions.ts` `createAccount`: creates the parent with `status: 'ACTIVE'`, not `'PREVIEW'`.
  A Google sign-up gets the column default, so it's ACTIVE too. The doc comments in `actions.ts` and
  `src/lib/auth.ts` that say "start as PREVIEW" are updated.
- Guards don't change. `requireActive` still refuses `PREVIEW` (only old rows have it now), with the same message,
  so the tests that make PREVIEW parents on purpose stay valid. A PREVIEW parent leaves PREVIEW by adding a child
  (below) or by an invite code, as today.

### 2. The parent adds their children: `families.addMyChildren`

`src/server/families.ts`, a new export:

```ts
addMyChildren = action(async (input: { children: { firstName: string; grade: number }[] }) => …)
```

- Guard `requireUser()`. Then `parse()`. Then `need(user.role === 'PARENT', …)`, and a PAUSED parent is refused
  with "Your account is paused. Message Vienne to turn it back on." (`FORBIDDEN`, as `redeemInvite` does).
- Input: `children` is 1 to `MAX_CHILDREN_AT_SIGNUP` (6) entries. Each `firstName` is trimmed, 1–40 characters,
  with no control character (S32's rule, `INVALID`, a plain message that names the field and never echoes it).
  `grade` is an integer from 0 to 6 (0 = K). The object isn't strict.
- It's for a parent with **no children yet**: one who signed up without a code. In one transaction, with the
  parent's row locked (`SELECT … FOR UPDATE` on `"User"`, so two taps can't both pass), it counts the parent's
  students. If there are any, it refuses with `CONFLICT`: "Your children are already on your account. Message
  Vienne to add another." Otherwise it does what `redeemInvite` does for planned children:
  - each child becomes a `Student` on this parent (`lastName: ''`, math as the subject, `schoolYear` from
    `Settings.timezone`);
  - the parent's `Conversation` is upserted;
  - a `PREVIEW` parent becomes `ACTIVE`.
  
  Queries run one at a time on `tx` (rule 13).
- It returns `{ students: [...] }` through the same student DTO the parent screens already read, so the adapter can
  refresh into Home.
- **The alert (S30's rule):** after the commit (rule 7), `notifyAdmins({ type: 'FAMILY_JOINED', title: 'New family
  joined: <parent name>', body: '<n> child(ren) added. They signed up without an invite code.', href:
  '/admin/families', parentId })`. There are no child names in the title, body or push, and it's linked only to
  the parent, so deleting a child leaves it. A parent who signs up and adds no child sends no alert.
- The code path is unchanged: `redeemInvite` still creates Vienne's planned children and sends `INVITE_REDEEMED`.
  The UI offers the code before "Add your child", so a parent normally does one or the other. If a parent with
  children enters a code anyway, the code still works, as it does today for a second code.

### 3. Limits

Every one is a named constant, listed in `docs/DEPLOY.md` → Limits and in p-sec's limits list.

| Constant | Where | Value | What happens |
|---|---|---|---|
| `SIGNUPS_PER_IP_PER_HOUR` | `actions.ts` | 5 | The 6th email sign-up from one IP in an hour: "Too many new accounts from here. Try again in an hour, or sign in if you already have one." Nothing is created. |
| `SIGNUPS_PER_HOUR` | `actions.ts` | 30 | Past 30 email sign-ups from everyone in an hour, sign-up pauses for the hour with the same message. The first refusal sends Vienne one alert, "New sign-ups are paused for an hour", as for invite codes. |
| `MAX_CHILDREN_AT_SIGNUP` | `families.ts` | 6 | `addMyChildren` takes up to 6 children. |
| `OPEN_REQUESTS_PER_FAMILY` | `scheduling.ts` | 5 | A 6th session request while 5 of the family's are still waiting (`REQUESTED`, in the future): `LIMIT`, "You have 5 requests waiting for Vienne. Wait for her answer, or message her." Vienne's own bookings don't count. |
| `MESSAGES_PER_DAY` | `messages.ts` | 50 | A parent's 51st message in 24 hours: `LIMIT`, "That's a lot of messages today. Vienne will read them; try again tomorrow." Vienne is never limited. |
| `MAX_UPLOADS_PER_DAY` | `storage.ts` | 200, unchanged | Already counted per parent per day. Open sign-up makes this the storage cap per account; see "For Javaris". |

- Sign-up counting works as L2's does. The IP comes from `clientIp()` and is stored only as
  `sha256(ip + ':' + INVITE_PEPPER)`, and a `null` IP shares one bucket. A new `SignupAttempt { id, ipHash,
  createdAt }` (indexed `[ipHash, createdAt]` and `[createdAt]`) is written for every sign-up that passes the zod
  check, including "There's already an account with that email". Counting and inserting happen in one transaction
  under `pg_advisory_xact_lock(7_300_530_003)`. The daily job (`src/lib/jobs.ts`) deletes attempts older than a
  day.
- Google sign-up isn't counted: Google verifies the address and rate-limits its own sign-in.
- `OPEN_REQUESTS_PER_FAMILY` and `MESSAGES_PER_DAY` are checked under a per-parent advisory lock
  (`hashtext('request:<id>')` and `hashtext('message:<id>')`, as uploads do), so taps at the same moment can't
  slip past.

### 4. Booking and pausing don't change

`requestSession` still makes a `REQUESTED` session that Vienne confirms or declines, and its alert is unchanged.
`setParentStatus` still pauses and unpauses. A paused parent can't add children, book or upload, and can still
message (S9).

### 5. The landing form

L2's `requests.requestInvite` stays as it is: same endpoint, limits and honeypot. Only the alert title changes,
from "Invite request from <name>" to "Question from <name>", because the form becomes "Questions? Message
Vienne". Type `INVITE_REQUEST`, the body and the 90-day clean-up don't change.

## Checks (for `plan/features.json`)

1. Email sign-up (`createAccount`) and Google sign-up both make an `ACTIVE` parent. `UserStatus` still has
   `PREVIEW`, the migration only adds (a default and `SignupAttempt`), and drift is green.
2. `addMyChildren` as a new parent with no children:
   - it makes each child a student on that parent (math, the school year) and returns them;
   - a PREVIEW parent becomes ACTIVE;
   - each admin gets one `FAMILY_JOINED` alert whose title, body and push name the parent and the count and no
     child's name.
   
   A second call, or a call from a parent who already has children (by code or by this), is `CONFLICT` and adds
   nothing. Two calls at once add one set.
3. Wrong input is `INVALID` with a plain message that never echoes the input. That covers: no children; 7
   children; an empty or 41-character name; a control character; grade −1, 7 or 2.5. A parent who is PAUSED is
   `FORBIDDEN`, a signed-out caller is `UNAUTHENTICATED`, and Vienne is refused. Nothing is stored in any case.
4. With a code, nothing changes: `redeemInvite` behaves as before (the s5 and s5b tests stay green), and booking
   still makes a `REQUESTED` session that Vienne answers.
5. Limits:
   - the 6th email sign-up from one IP in an hour is refused while another IP gets through;
   - past `SIGNUPS_PER_HOUR` everyone is refused, and Vienne gets one alert per hour;
   - a 6th waiting request is `LIMIT` (a confirmed or past one doesn't count);
   - a 51st message in a day is `LIMIT`, and Vienne's messages are never limited;
   - two requests or two messages at once on the last slot store one;
   - the daily job deletes `SignupAttempt` rows older than a day, and nothing else.
6. An ACTIVE parent with no children gets an ok, empty answer from every parent read the screens make before a
   child exists (Home's family read, notifications, messages), not an error.
7. p-sec:
   - `addMyChildren` is guarded (`requireUser` first);
   - it's in the permission and wrong-input sweeps;
   - the five new constants are in the limits list;
   - `ipHash` stays in `SECRET_KEYS`, and `SignupAttempt` is never returned.
   
   `docs/DEPLOY.md` → Limits lists them, and its "No limit in the app yet" lines for sign-up, messages and
   session requests are replaced by these limits.
8. Tests that expected PREVIEW after sign-up change, and only these lines:
   - `tests/e2e/auth.spec.ts` line 62: `status: 'PREVIEW'` becomes `status: 'ACTIVE'`. It's locked, so a lead
     makes the edit on the lane's PR, listed in `CHANGES.md`.
   - `tests/integration/s14-signup-password.test.ts` line 70, the same.
   
   Every test that makes a PREVIEW parent on purpose stays as it is and passes.

## For Javaris (no action unless he disagrees)

- **Anyone can now make an account and act as a family.** They can request sessions (each one alerts Vienne),
  message her and upload files. The new caps keep one account from flooding her: 5 waiting requests and 50 messages
  a day.
- **Storage:** uploads stay capped at 200 files a day per account, up to 25 MB each. That's fine for a real family,
  but now any stranger's account gets the same allowance. Lowering it for parents (say 40 a day) is a one-line
  change; say if you want it.
- **What families enter is real data** (their name, email, and their children's first names and grades). It's in
  the production database, never in the repo, as before. The privacy page should say that sign-up asks for
  children's first names and grades (Axis's copy).
- **Vercel Firewall** rate rules on `/sign-in` and `/api/auth/*` (Hardening) are still the real cap on bots.
