# L2: "Request an invite" on the landing page (Zero's part: endpoint, schema, limits)

Javaris, 2026-11-27 (via OSA): a family that isn't signed in can ask Vienne for an invite from the landing page. The
form asks for the parent's name, email, phone (optional), the child's grade and a message. The request shows up in
Vienne's alerts. No account is made, it's rate-limited, and there's a honeypot. Like every endpoint, it returns a DTO.

## The endpoint

`src/server/requests.ts`, `'use server'`, one export: `requestInvite = action(async (input) => …)`.

- **No guard, on purpose.** It's the only export anyone can call signed out. It goes in `PUBLIC` in
  `tests/integration/p-sec.test.ts` with the reason "the landing page's Request an invite form (L2): no account,
  rate-limited". It still calls `parse()` first, so p-sec's "only a guard may come first" check holds without an
  exception, and the wrong-input sweep still expects INVALID.
- **AGENTS.md rule 1** gets one sentence: "The one export without a guard is `requests.requestInvite` (L2). It's
  listed in p-sec's `PUBLIC` with its reason."
- **Input** (zod, in `src/lib/validate.ts` style):
  - `parentName` trimmed, 2–80
  - `email` (`z.email()`), lowercased, ≤ 254
  - `phone` optional, ≤ 30, only digits, spaces and `+ ( ) - .`
  - `grade` an integer 0–6 (0 = K, as elsewhere)
  - `message` trimmed, ≤ 1000, may be empty
  - `website`: the honeypot, optional string
  
  Refuse any control character (`/[\u0000-\u001f]/`, but allow `\n` in `message`), as S32 does, with
  `INVALID` and a plain message that names the field and never echoes the text. The object isn't strict.
- **Honeypot:** if `website` is non-empty, return the same success as a real request and write nothing.
- **What it returns, every time it succeeds:** `{ received: true }`. It's the same for a new request, a duplicate
  and a honeypot hit, so the answer never says whether an email has asked before. It never returns the input or an id.

## Limits (constants at the top of `requests.ts`, listed in DEPLOY → Limits and in p-sec's limits list)

| Constant | Value | What happens |
|---|---|---|
| `REQUESTS_PER_IP_PER_HOUR` | 3 | The 4th from one IP in an hour: `LIMIT`, "You’ve sent a few requests already. Vienne will reply by email; try again later if you need to." |
| `REQUESTS_PER_HOUR` | 20 | Over 20 from everyone in an hour: `LIMIT`, same message. The first refusal in an hour also sends Vienne one alert ("Invite requests are paused for an hour"), like the invite-code pause. |
| `DUPLICATE_EMAIL_HOURS` | 24 | A second request from the same email within 24 h: success, but no new row and no alert. |
| `REQUEST_KEEP_DAYS` | 90 | The daily job deletes requests, and their alerts, older than this. |

- The IP comes from `clientIp()` in a new `src/lib/client-ip.ts` (`server-only`). It reads `x-forwarded-for`'s
  first entry, then `x-real-ip`, from `headers()`, and returns `null` outside a request. Vercel sets these headers
  itself. Only a hash is stored: `sha256(ip + ':' + INVITE_PEPPER)`. A `null` IP still counts, under one shared
  bucket. Integration tests may `vi.mock('@/lib/client-ip')`; it isn't a guard.
- Counting and inserting happen in one transaction under `pg_advisory_xact_lock(<new constant>)`, so two requests
  at once can't both take the last slot. Queries run one at a time on `tx` (rule 13).

## Schema (one add-only migration, `npx prisma migrate dev --name invite_requests`)

```prisma
/// L2: a signed-out family asked for an invite. No account. Kept REQUEST_KEEP_DAYS, then the daily job deletes it.
model InviteRequest {
  id         String   @id @default(cuid())
  parentName String
  email      String
  phone      String?
  grade      Int
  message    String
  ipHash     String
  createdAt  DateTime @default(now())
  @@index([createdAt])
  @@index([email, createdAt])
  @@index([ipHash, createdAt])
}
```

`Notification` gets one nullable column, `inviteRequestId String?`, with no foreign key, the same way S23b added
`studentId` and `parentId`. The daily job deletes alerts by that id when it deletes their request, never by text.

## The alert

After the transaction commits (rule 7), `notifyAdmins({ type: 'INVITE_REQUEST', title: 'Invite request from <parentName>', body: '<grade label> · <email>[ · <phone>]\n<message>', href: '/admin/families', about: <request id>, inviteRequestId })`.
- The push carries only the title. Its tag is `INVITE_REQUEST:<id>`, as today.
- React escapes the body, so no HTML is built anywhere.
- Making the invite stays Vienne's job, on Families → Invite codes, as today. L2 adds no pre-fill.

## Checks (for `plan/features.json`)

1. Signed out, a valid request returns `{ ok: true, data: { received: true } }`, stores one `InviteRequest` and
   gives each admin one `INVITE_REQUEST` alert with the name, grade, email, phone and message. A parent gets no alert.
2. A filled `website` returns the same data and stores nothing and alerts nobody. So does a second request from the
   same email within `DUPLICATE_EMAIL_HOURS`.
3. Wrong input (every field: missing, too long, wrong type, a control character, grade 7 or −1, a bad email) is
   `INVALID` with a plain message that never echoes the input, and it stores nothing.
4. The (`REQUESTS_PER_IP_PER_HOUR` + 1)th request from one IP in an hour is `LIMIT`, while another IP still gets
   through. Past `REQUESTS_PER_HOUR` everyone is `LIMIT`, and Vienne gets one pause alert per hour, not one per
   refusal. A test that fires 2 at once on the last slot stores exactly one.
5. The response never carries the request's id, the input, `ipHash` or whether the email asked before. The leak
   sweep in p-sec covers `requests.requestInvite`, and `ipHash` is in its `SECRET_KEYS`.
6. The daily job deletes requests older than `REQUEST_KEEP_DAYS` and their alerts by `inviteRequestId`, and
   nothing else. A test leaves one 89 days old and removes one 91 days old.
7. p-sec: `requestInvite` is in `PUBLIC` with its reason, its four limits are in the limits list, and
   `docs/DEPLOY.md` → Limits lists them. The migration only adds, and drift is green.
8. The landing form (L1's page, L2's component) sends this and shows "Thanks. Vienne will email you soon." on
   success, or the plain message on `LIMIT` or `INVALID`, with no console errors. The honeypot field is hidden from
   people (off-screen, `tabindex="-1"`, `autocomplete="off"`, `aria-hidden`) and screen readers. An e2e test sends one
   as a signed-out visitor and finds the alert as Vienne.
