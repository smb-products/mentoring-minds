# S23b: delete on request, matched by ids only (Zero's spec for the plan)

S23 was reopened twice, and both reopens came from matching by text: an email `LIKE` pattern (an underscore
matched any character, so another family's code went), and children's and parents' names (first name only,
case-sensitive) for invite codes and alerts. S23b replaces every text match with an id. The rule:

> A delete removes a row only when an id ties it to the child or the parent being deleted. It never matches
> an email, a name, a title or any other text.

## What ties a record to a family, by id

| Record | The id that ties it | Today |
|---|---|---|
| Child's records (sessions, notes, homework, answers, FAST, reports, redo, shares, subjects) | `studentId` | already by id (S23) |
| Parent's records (thread, messages, push devices, sign-in links, wrong-code rows, own alerts) | `parentId` / `userId` / `senderId` | already by id |
| The invite code the parent used | `Invite.usedById` | by id, plus text matches (removed) |
| A child's line on that code (`plannedStudents`) | **new:** `studentId` on each entry, written by `redeemInvite` when it creates the student | by name (removed) |
| Vienne's alerts about a child or a family | **new:** `Notification.studentId` and `Notification.familyId`, set by the caller | by name (removed) |
| Files | `fileId` links (`dropUnusedFiles`, S17's in-use check) | already by id |

An **unused code** (never redeemed) is tied to no account, so the app doesn't touch it. It holds only what
Vienne typed. The runbook step tells her to revoke or delete any she made for that family on Invite codes.

## Schema (add-only, one migration)

- `Notification.studentId String?` → `Student`, `onDelete: Cascade`.
- `Notification.familyId String?` → `User` (the parent the alert is about), `onDelete: Cascade`.
- No column for `plannedStudents`: it stays Json, and its entries gain an optional `studentId`.
- Javaris runs `migrate deploy` before promoting the release (D5).

## Callers

- `notify` / `notifyAdmins` (`src/lib/notify.ts`) take optional `studentId` and `familyId` and store them. They
  sit next to S26's `about`, which stays push-only.
- Every caller that has the child or the family passes them:
  - `assignments`: given (to the parent), handed in (to Vienne), graded, returned.
  - `scheduling`: requested, confirmed, declined, cancelled either way, moved, booked by Vienne.
  - `reports`: published.
  - `messages`: received, with `familyId` = the thread's parent.
  - `invites`: redeemed (`familyId`), and the guessing alert (no family: neither).
  - `jobs`: reminders.
- `redeemInvite` writes the new student's id into its `plannedStudents` entry, inside the same transaction.

## What deleteStudent removes (one transaction, then the files)

1. Sessions of the child (their notes and note skills cascade), and Vienne's AI note drafts whose `refId` is
   one of those sessions.
2. Redo items, submissions, assignments that only this child had, progress reports (ratings cascade).
3. Alerts with `studentId` = the child, for any recipient (cascade, or an explicit delete before the child).
4. On the parent's used code (`usedById` = parent), the `plannedStudents` entry whose `studentId` = the child.
   The code stays, with its other entries.
5. The child (FAST results, redo list, shares and subjects cascade).
6. After commit: the stored files only the child's records used (`dropUnusedFiles`).

## What deleteFamily removes

1. Every child, as deleteStudent.
2. The parent's thread (messages cascade). Messages the parent sent anywhere else.
3. The code the parent used (`usedById` = parent).
4. Alerts with `familyId` = the parent, for any recipient.
5. Their marks on rows that stay, by id: `requestedById` becomes Vienne, `cancelledById` and `submittedById`
   become null, and FAST results they entered for anyone else are removed (as today).
6. Their uploads that nothing else uses (`dropUnusedFiles`). An upload something else still uses stays, as Vienne's.
7. The parent's account. Sign-in links, push devices, wrong-code rows and their own alerts cascade.
8. After commit: the stored files from step 6.

It never deletes or edits a code, an alert or any other row that only text ties to the family.

## Checks (for the plan)

1. `deleteStudent` and `deleteFamily` remove exactly the rows listed above, matched only by the ids in the
   table. `git grep` in `src/server/families.ts` finds no `contains`, `mode: 'insensitive'`, `parentEmail`,
   `parentName` or `firstName` in a `where:`.
2. Another family is never touched, even when its parent's email differs only by a character that a pattern
   would treat as a wildcard (`ana_m` / `anaxm`), its names are the same in any case, or its child has the same
   first name. Its codes, alerts and children stay exactly as they were. (These are the holdout's cases.)
3. A child typed in any case on the family's code is removed from that code, because `redeemInvite` wrote
   their `studentId`. A code redeemed before S23b (dev data only) keeps its entries. The report says so.
4. Alerts about a deleted child or family go for every recipient, Vienne included. Alerts about anyone else
   stay, whatever their title says.
5. Permissions as in S23: admin only, Vienne's own account can't be deleted, missing ids give NOT_FOUND, and
   the two-step confirm on the family page is unchanged.
6. The migration adds only. `npm test` (with p-sec's migration checks), `test:contract`, the S23 holdouts in
   `tests/holdout/` and `plan/holdouts/S23.test.ts`, and the browser suite pass.
